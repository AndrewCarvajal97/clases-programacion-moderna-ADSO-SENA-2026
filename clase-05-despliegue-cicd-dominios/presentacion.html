Concepto

¿Qué es desplegar (deploy)?

Llevar tu proyecto de tu computador a internet, con un link que cualquiera puede abrir.

💻 En tu PCsolo tú lo ves
☁️ Servidorencendido 24/7
🌍 Internettodos lo ven

Un servidor es solo un computador siempre encendido que entrega tu página cuando alguien la pide.

🧭 LA GRAN DIVISIÓN

Dos tipos de web (clic para comparar)

🧊 Estática
archivos ya listos: HTML, CSS, JS
tu portafolio
El servidor solo entrega archivos, iguales para todos. Rápida, barata y a menudo gratis. Ej: portafolios, landing pages, blogs. Hosting: estático (GitHub Pages, Netlify).
⚙️ Dinámica
un servidor genera la respuesta
redes, tiendas, apps
Hay código corriendo (Node, PHP, Python) y casi siempre una base de datos. La página cambia según el usuario. Ej: red social, tienda, panel. Hosting: de apps (Render, Railway, un servidor).

Saber cuál es tu proyecto decide dónde y cómo lo despliegas. Hoy publicamos lo estático; lo dinámico llega con el backend.

🌐 DOMINIOS

¿Qué es un dominio y cómo funciona?

Un dominio es el nombre fácil de tu sitio (tuweb.com). El DNS lo traduce a la IP del servidor.

⌨️ tuweb.comlo que escribes
📖 DNStraduce nombre → número
🔢 203.0.113.5IP del servidor
🖥️ Servidorentrega la página

Analogía: el DNS es la agenda de contactos de internet — tú marcas el nombre, ella conoce el número.

🆓 GRATIS

Cómo conseguir un dominio gratis

1 · Subdominio del host

Ya viene incluido: usuario.github.io, tu-sitio.netlify.app, *.vercel.app. Cero pasos, gratis para siempre. Suficiente para el curso.

2 · 🎓 GitHub Student Pack

Con correo institucional o carnet: un dominio 1 año gratis (Namecheap .me, name.com, .tech…) + créditos en la nube.

3 · Dominios de comunidad

Para proyectos: *.js.org, *.is-a.dev, *.eu.org — gratis, se piden por solicitud/PR en GitHub.

⚠️ Evita los "TLD gratis" dudosos (tipo Freenom/.tk): se caen y te quedas sin sitio. Mejor las 3 vías de arriba.

Apuntar el DNS

Conectar tu dominio al host

1 En el panel de tu dominio, entra a DNS.

2 Crea un registro A → la IP del host (o un CNAME → su dirección).

3 En el host, agrega tu dominio (“Custom domain”).

4 Espera la propagación y activa HTTPS (candado). ✅

🤖 CI/CD

¿Qué es CI/CD?

CI · Integración Continua

Cada cambio que subes se junta y se revisa (se compila y se prueba) automáticamente.

CD · Despliegue Continuo

Si todo pasó, se publica solo en internet. Sin subir archivos a mano.

En una frase: "subo mi código y la web queda probada y actualizada sola".

La tubería (pipeline)

Las etapas de un pipeline CI/CD

✏️ Commitsubes código
🔨 Buildconstruye
🧪 Testprueba
🚀 Deploypublica

Si una etapa falla, la tubería se detiene y no publica. Así un error no llega a producción. 🛡️

⚙️ GITHUB ACTIONS

Anatomía de un workflow (YAML)

# .github/workflows/deploy.yml
on: [push]              # CUÁNDO se ejecuta (al subir código)
jobs:                    # TRABAJOS a realizar
  build:
    runs-on: ubuntu-latest  # DÓNDE: una máquina en la nube (gratis)
    steps:                 # PASOS, en orden
      - run: npm ci && npm test

on = el disparador · jobs = qué hacer · runs-on = en qué máquina · steps = los pasos.

🧊 SITIO ESTÁTICO

CI/CD para una página estática

on:
  push: { branches: [main] }        # al subir a main
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4       # baja tu código
      - run:  npm ci && npm run build   # construye el sitio → dist/
      - uses: actions/deploy-pages@v4    # lo publica en Pages

Si tu sitio no usa herramientas (solo HTML/CSS/JS), Pages lo publica sin build. Con Vite/Astro/React, el build arma el dist/.

⚙️ APP DINÁMICA

CI/CD para una app con servidor y BD

jobs:
  test:                              # 1) CI: probar ANTES de publicar
    runs-on: ubuntu-latest
    steps: [ { run: npm ci && npm test } ]
  deploy:
    needs: test                      # solo si las pruebas pasan
    runs-on: ubuntu-latest
    steps:
      - run: npm run migrate          # 2) actualiza la base de datos
      - run: ./deploy.sh              # 3) CD: publica en el servidor/Render
        env: { API_KEY: ${{ secrets.API_KEY }} }

Lo nuevo vs estático: pruebas, migraciones de base de datos y secretos. Y needs encadena: no publica si algo falló.

🔑 SEGURIDAD

Secretos y variables de entorno

❌ Nunca en el código

const key = "sk_live_123abc"; // ¡NO!

Cualquiera lo ve en el repo o con F12. Se filtra para siempre.

✅ Fuera del código

# local: archivo .env (en .gitignore)
API_KEY=sk_live_123abc
# en CI: GitHub → Settings → Secrets
env: { KEY: ${{ secrets.API_KEY }} }

Regla de oro: claves, contraseñas y tokens van en secretos/variables de entorno, nunca en el repositorio.

☁️ LA NUBE

¿Qué es "la nube"?

La nube es el computador de otra persona: servidores de una empresa (AWS, Azure, Google Cloud) que alquilas y usas por internet.

Pagas por uso

Como la luz: pagas lo que consumes, sin comprar máquinas.

Escala al instante

¿Llegaron 10.000 usuarios? Pides más servidores en minutos.

Sin mantenimiento físico

Ellos ponen el hardware, la energía y la refrigeración.

🏢 vs ☁️

Nube vs On-premise (clic para comparar)

☁️ En la nube
servidores alquilados
flexible
Rápido de arrancar, escala solo, pagas por uso (gasto operativo). Menos control físico y dependes del proveedor. Ideal para empezar y crecer.
🏢 On-premise
servidores tuyos, en tu edificio
control total
Control y datos en casa (útil por normativa/seguridad). Pero compras el hardware (gasto inicial alto), lo mantienes tú y escalar es lento. Común en bancos, hospitales, gobierno.

Muchas empresas mezclan las dos: es lo que se llama nube híbrida.

Modelos de servicio

IaaS · PaaS · SaaS 🍕

IaaS

Infraestructura. Te dan la máquina "vacía"; tú instalas todo.
Pizza: te dan la cocina. (AWS EC2)

PaaS

Plataforma. Subes tu código y ellos lo corren.
Pizza: te la hacen, tú eliges ingredientes. (Render, Vercel)

SaaS

Software listo. Solo lo usas desde el navegador.
Pizza: te la entregan lista. (Gmail, Canva)

Cuanto más a la derecha, menos gestionas tú (y menos controlas). Para el curso usamos PaaS (fácil).

⚖️ ALTA DEMANDA

Balanceadores de carga

Cuando un servidor no da abasto, pones varios y un balanceador reparte el tráfico entre ellos.

👥 Usuarios
⚖️ Balanceadorreparte el tráfico
🖥️ Servidor 1
🖥️ Servidor 2
🖥️ Servidor 3

Ventajas: aguanta más usuarios, y si un servidor se cae, el balanceador manda el tráfico a los otros (alta disponibilidad). 🛡️

Crecer

Escalar: vertical vs horizontal

↕️ Vertical

Una máquina más potente (más RAM/CPU). Simple, pero tiene tope y si se cae, se cae todo.

↔️ Horizontal

Más máquinas trabajando juntas (con balanceador). Escala casi sin límite y tolera caídas. Es como funciona internet a gran escala.

Regla moderna: cuando puedas, escala horizontal (muchas máquinas pequeñas) en vez de una gigante.

🖥️ ESCRITORIO

Electron: apps de escritorio con web

Electron junta Chromium (un navegador) + Node.js para que tu HTML/CSS/JS sea una app de escritorio instalable (Windows, Mac, Linux).

VS CodeDiscordSlackWhatsApp DesktopFigma

Todas esas son Electron: por dentro son una web, pero se ven y se instalan como un programa normal. Una base de código para los 3 sistemas.

Dos procesos

Cómo funciona por dentro

🧠 Proceso principal (main)

Es Node.js: crea las ventanas y habla con el sistema (archivos, menús, notificaciones).

🪟 Proceso de ventana (renderer)

Es Chromium: pinta tu HTML/CSS/JS, como una página web dentro de la app.

mainNode · sistema
IPCse comunican
renderertu web

Se hablan por IPC (mensajes). Alternativa más liviana: Tauri (usa el navegador del sistema, pesa mucho menos).

Empaquetar y entregar

Desplegar una app de escritorio

Empaquetar

electron-builder genera los instaladores: .exe (Win), .dmg (Mac), .AppImage (Linux).

Firmar

Firmar la app evita el aviso de "editor desconocido" y que el antivirus la bloquee.

Auto-update

La app se actualiza sola desde un servidor de releases (p. ej. GitHub Releases).

💡 CI/CD también aplica aquí: un workflow puede construir los 3 instaladores en cada versión y subirlos a Releases.

⭐ MEJORES PRÁCTICAS

Despliegue y CI/CD como los pros

✅ Haz

  • Automatiza el deploy (CI/CD), no subas a mano.
  • Prueba antes de publicar; si falla, no sale.
  • Secretos fuera del código; HTTPS siempre.
  • Separa entornos y ten rollback y backups.

❌ Evita

  • Subir por FTP a mano "a ver si funciona".
  • Contraseñas en el repositorio.
  • Desplegar el viernes a las 6pm sin pruebas.
  • Un solo servidor sin respaldo ni monitoreo.

Y observa: logs y monitoreo te avisan si algo se rompe antes que el usuario. 📈

📖 EL SUPERPODER

Saber leer documentación

La habilidad #1 del dev: nadie memoriza todo; los buenos saben buscar y leer la doc oficial.

✅ El método

  • Ve a la fuente oficial (no un blog viejo).
  • Busca "Quickstart"; haz funcionar el ejemplo mínimo.
  • Cambia una cosa a la vez; usa Ctrl+F.
  • Revisa la versión; lee el error completo.

🤖 Con IA

La IA ayuda a entender, pero verifica en la doc oficial: la IA se equivoca, la doc es la verdad.

Analogía: la doc es el manual del juego. Quien lo lee juega mejor que quien adivina los controles.
